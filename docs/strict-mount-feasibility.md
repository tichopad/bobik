# Strict mount propagation on Ubuntu

**Keep the strict check.** Stock Bubblewrap cannot provide private binds from this host's shared mount tree by changing flags. The best candidate is a maintained Bubblewrap build with recursive `MS_PRIVATE` instead of `MS_SLAVE` during setup, ideally an upstream option. It should require no per-run sudo or user-invoked wrapper, but the patched build and its AppArmor policy have not been tested. Until they pass preflight, fail closed.

## What is established

- On this host (`7.0.0-42-generic`, Ubuntu Bubblewrap `0.9.0-1ubuntu0.3`, non-setuid), `/` and `/dev` are `shared`. A disposable gated launch as UID/GID 1000 using `--ro-bind-fd` for `/usr` and `--dev-bind` for `/dev/null` produced `master:1` and `master:2`, respectively. The host parent could read the blocked child's `mountinfo`, open its final `/proc/<pid>/root`, and match `/usr` against the pinned fd; its UID/GID maps were `1000 → 1000`. The child's setup label was `bobik-bwrap (unconfined)`, attached to `/usr/bin/bwrap` with `userns,`. This was a plumbing probe, not a Bobik preflight. A plain `unshare --user --map-current-user --mount --propagation private …` failed writing `uid_map`; without the map option it failed changing propagation. The separately reported `sudo unshare --mount --propagation private` then `runuser` success is a useful control, not an unprivileged solution.
- Linux turns shared mounts into slaves when copying the tree into a mount namespace owned by a different user namespace. A slave still **receives** events; binding a slave onto a non-shared mount preserves its master. A private mount neither sends nor receives events. Read-only/nosuid/nodev on an existing bind do not seal propagation or apply to later propagated mounts. A snapshot allowing `master:` cannot enforce the strict requirement. This is about mount events, not live file writes or renames on a shared filesystem. [Kernel shared-subtree docs](https://docs.kernel.org/filesystems/sharedsubtree.html), [mount namespaces and mountinfo tags](https://man7.org/linux/man-pages/man7/mount_namespaces.7.html), [Bubblewrap remount code](https://github.com/containers/bubblewrap/blob/v0.13.1/bind-mount.c#L510-L535).
- Upstream [0.9.0](https://github.com/containers/bubblewrap/blob/v0.9.0/bubblewrap.c#L3070-L3085), [0.13.1 (latest release checked)](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L3271-L3285) and [checked main](https://github.com/containers/bubblewrap/blob/1fb0aa26d3eb66254f7742e704add7f82f41a582/bubblewrap.c#L3271-L3285) deliberately use `MS_REC|MS_SLAVE` before creating the sandbox root and its binds. The [later `MS_PRIVATE`](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L3328-L3343) is for `/oldroot` before detaching it, not the cloned binds in `/newroot`. Neither installed CLI help nor [current CLI options](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L287-L370) offer a propagation switch or a way to supply a mount namespace. `--remount-ro`, `--unshare-all`, and `--as-pid-1` don't change this. The installed package backports fd bind flags absent from vanilla 0.9.0; see the installed package changelog and [upstream 0.10.0's fd source resolution and identity check](https://github.com/containers/bubblewrap/blob/v0.10.0/bubblewrap.c#L1237-L1257).

## Options and costs

- **Patched Bubblewrap — first choice to test.** Replace the *early* recursive slave operation with private, keeping failure fatal. Bubblewrap already owns that new mount namespace through its child user namespace; this requires no initial-namespace capabilities. The [current fd bind implementation resolves the fd path](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L1646-L1670) and [opens the source under the copied old root, then checks its identity](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L1229-L1308); thus inherited fd binds should also pick up the private source mounts. Verify, don't assume: an fd pins a particular mount/dentry, and a future implementation that directly uses a foreign mount fd need not behave the same way ([Linux bind path/clone code](https://github.com/torvalds/linux/blob/v7.0/fs/namespace.c#L2960-L3029)). Keep Bobik's root-owned executable checks ([runtime lookup](../internal/sandbox/runtime_linux.go)); shipping a private helper at a new path needs an equally trusted lookup and a policy for that path. Prefer an upstream opt-in; bundling a fork means owning security updates, distro packaging and amd64/arm64 test coverage.
- **Internal launcher + distro Bubblewrap — plausible, more moving parts.** A small single-threaded helper, or child created with both `CLONE_NEWUSER|CLONE_NEWNS`, can use namespace-local `CAP_SYS_ADMIN` to call `mount(NULL, "/", NULL, MS_REC|MS_PRIVATE, NULL)` **before** exec and before it loses caps. Linux creates the user namespace first; permission to change propagation is checked against the mount namespace's owning user namespace. Do not unshare from arbitrary Go runtime threads or make the live Bobik process enter the namespace. Map the ordinary UID/GID through (handle `setgroups`/`gid_map`); keep the host PID namespace for the launcher and use an exec chain so the status PID, process group, parent-death, limits and cancellation remain intact. Avoid passing retained capabilities to a nonzero-UID bwrap, which rejects them. Keep its own explicit `--unshare-user --disable-userns`: Bubblewrap sets a scoped nesting limit, creates another user namespace and tests that further creation fails. The outer namespace costs another nesting level and can affect proc credentials, supplementary groups, fd/path resolution, and filesystem/LSM access. `--userns` conflicts with `--unshare-user`, and `--disable-userns` requires the latter and conflicts with `--userns-block-fd`; `--userns2` switches user namespaces after mount setup in the child, and `--assert-userns-disabled` only checks, not enforces. [Linux user namespaces and maps](https://man7.org/linux/man-pages/man7/user_namespaces.7.html), [propagation permission](https://github.com/torvalds/linux/blob/v7.0/fs/namespace.c#L2830-L2893), [Bubblewrap flag validation](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L2953-L2973), [capability check](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L792-L828), [late userns setup](https://github.com/containers/bubblewrap/blob/v0.13.1/bubblewrap.c#L3376-L3429).
- **AppArmor is separate from namespace capabilities.** On this Ubuntu host the existing exception attaches at `/usr/bin/bwrap` exec; it does not authorize a helper's earlier operations or automatically cover a different binary path. Cloning does not drop LSM policy, and exec may inherit or transition under the loaded rules. A one-time policy scoped to the dedicated root-owned launcher/build must cover the actual operations and exec transitions (UID/GID maps if used, mounts/pivots, private loopback, nested userns and host-side proc inspection). Verify both setup and payload labels; don't assume `userns,` alone in an enforcing profile is enough, or use a system-wide sysctl change, general-purpose `unshare` exception, or ptrace relaxation. Other LSMs, namespace limits or container seccomp can still block either design. [Ubuntu AppArmor restrictions](https://documentation.ubuntu.com/security/security-features/privilege-restriction/apparmor/#apparmor-unprivileged-user-namespace-restrictions), [AppArmor exec modes](https://manpages.ubuntu.com/manpages/noble/en/man5/apparmor.d.5.html), [`/proc/<pid>/root` access](https://man7.org/linux/man-pages/man5/proc_pid_root.5.html), [ptrace access checks](https://man7.org/linux/man-pages/man2/ptrace.2.html).

## Fastest decisive test

With separate approval, install a test build with the early `MS_PRIVATE` change under the intended dedicated AppArmor profile (or first use a disposable Ubuntu VM with shared `/` and `/dev`). Run the same gated probe from the ordinary account, with path binds, pinned writable/read-only fd binds from a disposable directory, and `/dev/null`. From the real host parent, check the final child's mount table for **no** `shared:`, `master:` or `propagate_from:`, verify UID/GID maps and `/proc/<pid>/root` identities, and confirm the expected AppArmor label, PID 1, namespace isolation, capability drop, and status/cancellation behavior. Then run `bobik check-sandbox` and `BOBIK_REQUIRE_SANDBOX=1 go test ./internal/sandbox` against exactly that build and policy. A disposable shared-parent tmpfs mount/unmount regression test can additionally confirm the absence of inbound events. Keep the existing topology, host alias/submount, inode, vault, seccomp, and command gate checks; a launch that fails any of them remains unavailable. If no upstream or maintainable verified build is available, document the strict deployment restriction rather than accepting slave binds. No host settings or vault were touched in this investigation.
